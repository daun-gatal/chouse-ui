# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [v3.18.1] - 2026-11-17

### Changed
- **One place for a connection's ClickHouse login** — a connection opens in one panel with **General**, **ClickHouse login** and **Who can query** tabs, and the separate *ClickHouse login* and *Linked ClickHouse users* buttons are gone. The login tab is one form (kind, host, port, TLS, user, password, default database, roles, access contact) with **Test**, which checks without saving, and **Save**. Changing the kind shows one hint that says what the kind needs, and the script for the ClickHouse administrator never contains the password.
- **Create a role-ceiling or personal connection directly** — choose the kind when creating; one ClickHouse user with no grants of its own is enough, and the same checks as a switch run first. **Who can query** opens next to map roles or link people.
- **Who can query** column in Admin › Connections and in the connection switcher: whether everyone a connection is meant for can use it, and for a person whose role isn't mapped, why and whom to ask.

### Fixed
- The default database can be changed on role-ceiling and personal connections, and cleared on any connection.
- A shared-login save that ran while a super admin switched the connection's kind could store a full-privilege login on the switched connection; login saves now apply only if the connection did not change meanwhile.
- The stored password and TLS rule, port and password limits, and the "one ClickHouse user per kind" check are the same everywhere the login is saved.
- A role-ceiling or personal connection nobody can query yet can no longer be made the default, and one turned back on is checked at once instead of being refused for up to five minutes.
- Refused attempts to create or switch a role-ceiling or personal connection are recorded in the audit log.
- **Security:** server dependencies `hono` (4.13.13 → 4.13.19) and `@hono/node-server` (2.1.3 → 2.1.8) are updated, clearing the 6 medium and 1 low findings Artifact Hub's Trivy scan reports for image 3.18.0 (CVE-2026-126210, CVE-2026-126343, CVE-2026-126355 to CVE-2026-126359).

## [v3.18.0] - 2026-11-15

### Added
- **What your statements run as, for agents and scripts** — a new MCP tool, `connection_runs_as`, and the CLI command `chouse connection runs-as` report which ClickHouse identity a caller's statements carry on each connection, whether it is usable now, and what a personal connection refuses. An agent can find out before its first statement instead of from a refusal.
- **Links from the command line** — a super admin can list, add, re-check and remove the links between accounts and ClickHouse users with `chouse connection links`, and print the GRANT script for the ClickHouse administrator.
- **Identity lab** — `testbed/identity-lab/` starts CHouse UI with PostgreSQL and two ClickHouse servers, seeded with one connection of each kind, to try them by hand.
- **A kind the ClickHouse server cannot run is blocked up front** — Admin › Connections › ClickHouse login now asks the connection's server which kinds it can run and disables the others before anything is typed, with the server's version and what the kind needs: the role ceiling needs ClickHouse 24.4 or newer, a personal connection needs the `EXECUTE AS` statement. It asks the server itself, not a version list. The Linked ClickHouse users panel warns when the server can never be a personal connection.
- **Role ceiling for connections** — a connection can now limit each person to a ClickHouse role. The connection's ClickHouse user holds no grant of its own; a super admin maps each CHouse role to one ClickHouse role, and every statement is sent with the role of the person it is for, so ClickHouse itself refuses anything outside it, for administrators too. CHouse UI's own background work uses a separate system role. Needs ClickHouse 24.4 or newer. Existing connections stay shared logins and behave as before.
- **Identity checks** — before a connection is switched, and every five minutes after, CHouse UI checks that its ClickHouse user is empty, that its roles cannot manage or become other users, that a request naming no role reads nothing, and that no other connection of a different kind uses the same user. A connection that fails, or was last checked more than 15 minutes ago, refuses every request and says why.
- **Access contact** — an optional line per connection, shown when ClickHouse refuses someone, saying whom to ask for access.
- **Identity panel in Admin › Connections** (super admin) — shows a connection's kind, health and role map, the statements for the ClickHouse administrator, and checks a new login before saving it.
- **Reads are sent read-only** — CHouse UI now asks ClickHouse itself to refuse a write. Every read (`SELECT`, `SHOW`, `DESCRIBE`, `EXISTS`, `CHECK`, `EXPLAIN`) is sent with `readonly = 2`, for administrators too, and so is every statement from a person whose roles hold no write permission. Whether a statement is a read comes from ClickHouse's parse of it. Dashboard panels, notebook cells, scheduled queries and data health checks are read-only for everyone.
- **Assign a job to yourself** — a scheduled query with no owner shows **No owner** in the list and on its page, with an **Assign to me** action for people who can edit it.
- **The connection switcher names the ClickHouse user** — each connection shows "Shared login <user>": the ClickHouse user every statement on it runs as.
- **Every ClickHouse statement names its account** — each request CHouse UI sends now carries a query id of the form `chouse:p:<account id>:<random>` (or `chouse:s:<purpose>:<random>` for background work) and, on ClickHouse servers that accept it (24.8 and 26.5 do, 23.8 does not), a quota key with the same account or purpose. A ClickHouse administrator can read the account from `system.query_log`, and a ClickHouse quota `KEYED BY client_key` now counts each CHouse account separately.
- **Personal connections** — a third connection kind. A super admin links each CHouse account to a ClickHouse user, and that person's statements run as that user (`EXECUTE AS`), so the grants, row policies and quotas already in ClickHouse decide what they reach. The connection's own ClickHouse user holds no grant; CHouse UI stores no password for the linked users. Existing connections are unchanged.
- **Server self-test** — a connection can be personal only on a ClickHouse build that checks the target user's grants for every statement run with `EXECUTE AS`. CHouse UI tests this before the switch and every five minutes, and again at most a minute before a statement runs as a person. Of the builds tested, 26.3.63 passes; 26.5.7 (it runs `CREATE` unchecked) and builds without `EXECUTE AS` are refused.
- **Links between accounts and ClickHouse users** — Admin › Connections › Linked ClickHouse users (super admin): create, confirm and remove links, see the `GRANT` to hand to the ClickHouse administrator, and the users the connection may still act as without a link. A link is suspended when someone else resets the account's password or changes its email, when a sign-in identity is added or removed, and on reactivation; it is disabled when the ClickHouse user was dropped and created again or gains a privilege that manages users.
- **Your ClickHouse user in Preferences and the connection switcher** — each person sees which ClickHouse user their statements run as on a personal connection, and the state of the link.
- **File import on a personal connection** — rows go in as the person, through a short ClickHouse session.

### Changed
- **A super admin reaches every active connection in every feature** — AI memories, the AI action inbox, Data Health, upgrade checks and the connections in the profile listed only connections a data access policy named, also for a super admin's browser session. They now list all active connections, as the rest of the product does.
- **Switching a connection's kind, editing its role map, and confirming or removing a suspended link need a browser session** — a personal access token or an agent can no longer do these, even a super admin's. They store credentials or decide what ClickHouse lets every account do.
- **A switch to an unsupported kind is refused with one reason** — the API answers 422 `KIND_UNSUPPORTED_ON_SERVER` with the server's version and what is needed, instead of `IDENTITY_CHECK_FAILED` with a list of checks that each failed for the same cause.
- **Only a super admin assigns a mapped role** — a CHouse role that is mapped to a ClickHouse role on any connection can be assigned only by a super admin. The same holds for changing an account that holds such a role or resetting its password, and for changing which role SSO assigns once any role is mapped.
- **Login changes on a role-ceiling connection go through the Identity panel** — host, port, TLS, user and password of such a connection can no longer be changed in the edit dialog.
- **ClickHouse users and roles are unavailable on a role-ceiling connection** — its login may not manage users.
- **The privilege report is per kind** — on a role-ceiling connection it checks the system role, and marks data editing as coming from each person's role.
- **System tables that show other people's work need a permission** — a typed read of `system.query_log`, `system.processes`, `system.text_log` and the other statement and session logs needs `query:history:view:all`; a read of `system.users`, `system.grants` and the other access tables needs `clickhouse:users:view`. Other system tables stay open. Without the permission, the Logs page still lists your own statements, and the parts of Monitoring that read these tables say which permission they need.
- **You see the scheduled queries you own** — without `scheduled_queries:view_all`, a job you created leaves your list once someone else becomes its owner, because its results are then read with their access.
- **A job runs as whoever last changed what it does** — saving a change to a scheduled query's SQL, output or notification channels makes the saver its owner, and later runs are checked against that person's access. The same holds for a data health check, and for a dashboard's alerts and reports when someone changes a panel's SQL or the dashboard's variables. Existing jobs keep their creator as owner.
- **Ownership is read from the query id** — Live Queries, the Logs page, lineage, table usage and the AI tools that list your own queries read the CHouse account from the query id CHouse UI set. A statement that sets its own `log_comment` no longer changes who it is shown for, and cannot hide itself from CHouse UI's reports.
- **The fleet AI checks the SQL it writes** — statements the Doctor and the other fleet AI features write for a person are parsed by ClickHouse, may read only system tables, and follow the same permission rule for the statement logs.
- **Clearer messages when ClickHouse refuses** — a refused write reads "You may only read here", a missing ClickHouse grant names the grant, and neither is reported as a sign-in failure any more. A connection whose stored login ClickHouse rejects reports `CONNECTION_AUTH_FAILED` instead of signing you out.
- **One module sends every statement** — all server code now reaches ClickHouse through a single executor that requires a person or a named background purpose for each request. A CI check fails when any other file imports the ClickHouse client. The design is ADR 0033.
- **`EXECUTE AS` is refused for everyone** — a typed statement that contains `EXECUTE AS` anywhere in ClickHouse's parse of it is not run, for administrators too.
- **Administrators' statements are parsed first** — a statement typed by an admin is parsed by ClickHouse before it runs. Permission and data access checks are still skipped for admins, but a statement ClickHouse cannot parse, or cannot parse right now, is refused.
- **Typed `KILL QUERY` needs `live_queries:kill_all`** — it can target anyone's query. `live_queries:kill` still stops your own queries from Live Queries and the editor's Stop button.
- **Scheduled jobs need an owner** — a scheduled query or data health check with no owner no longer runs; its runs fail with the reason. Saving such a job makes the person who saved it the owner.
- **Query id format** — ids CHouse UI sets are no longer bare UUIDs. AI queries are `chouse:p:<account id>:chouse-ai-<request id>-<n>`.
- **On a personal connection** data access rules do not decide what a statement reaches (the person's ClickHouse user does; rules still limit collected monitoring evidence), `SET`, `USE`, `INSERT … VALUES` and a typed `FORMAT` clause are refused, only statement kinds on a tested list run, and materialize jobs, ClickHouse user management and background reads of table data are unavailable.

### Fixed
- **Monitoring table lists follow data access rules** — on Metrics, the largest tables, replication and parts pressure lists (and the same lists in the production overview) now show only the tables the signed-in user can read. Admins still see every table.
- **Mutation impact simulator checks data access** — the simulator now applies the user's data access rules to the table and to anything its predicate reads, the same way the SQL editor checks a query.
- **Notebook query cells keep their rows to permitted readers** — a query cell's saved rows are shown only to readers whose own data access rules allow that query. Other readers see the SQL and a note that the rows are withheld, in the notebook and in its Markdown export.
- **Sample error messages on Metrics** — sample error text is shown only to admins and holders of `query:history:view:all`; everyone else still sees the error counts.
- **AI tools list only your own queries** — for non-admins, the running-queries and slow-queries tools now return only queries run by the same CHouse account.
- **Stopping a query needs a confirmed owner** — without `live_queries:kill_all`, a query whose owner can't be confirmed is no longer stopped.
- **A scoped personal access token is held to its scopes everywhere** — a token whose scopes were narrowed could still pass permission checks on routes outside them when its owner held the permission. Every permission check for a token's request now answers from the token's own scopes. **If you rely on a scoped token for something outside its scopes, it now gets 403: add the permission to the token's scopes, or create a new token.** Tokens without scopes and browser sessions are unchanged.
- **An administrator's scoped token is held to its scopes in the SQL editor routes** — a statement from an administrator skips the permission check for its kind, and that applied to a scoped token too. A scoped token is now checked like anyone else's for the kind of statement (select, insert, DDL) and for the system tables that need a permission. Data access rules still do not restrict an administrator's token.
- **A scoped token does not act as an administrator** — an admin's or super admin's token kept the role whatever its scopes, so features that let an administrator act without a permission did not hold it to them. A scoped token no longer carries the admin or super admin role: it cannot see other people's dashboards or scheduled queries, approve high-risk actions, assign the super admin role, or change a connection's kind, role map or linked ClickHouse users. Use a browser session or a token without scopes for those. It still reaches the same connections as its owner.
- **The profile shows what a token carries** — `whoami` over MCP and `chouse auth whoami` listed the owner's permissions and roles for a scoped token. They now list the token's own.
- **Account names in the GRANT script** for linked ClickHouse users are written as plain comment text.
- **Connection details in the profile** — for someone who is not a super admin the profile no longer includes a connection's role names, server version or the reason a check failed, as on the connection list.
- **Linking a chat account needs a browser session** — creating a Telegram link code and unlinking a chat account are refused for a personal access token, like other actions that decide who can act as you.
- **The scheduled query preview read the query's columns before checking access** — the materialize preview now sends nothing to ClickHouse unless your data access allows the query.
- **Typed text could reach ClickHouse without the check it was shown** — the server now sends a typed statement only as the exact text, parameters, connection and account the access check approved.
- **Column names in a file import** are written as quoted identifiers, so a name with a space or another special character imports correctly and is never read as SQL.
- **`DELETE FROM` and `UPDATE` in the SQL editor** — a lightweight delete or update typed in the editor failed with a syntax error at `FORMAT`. They now run as commands, on every connection kind.

## [v3.17.2] - 2026-11-11

### Added
- **Other databases in Test connection** — data editing is only checked on the connection's default database, so the privilege report now also lists, for information, what the user can do in each other database (query all or some tables, change tables or not) with the `GRANT` statements for full access. It never blocks a save.

### Changed
- **Connections save without ClickHouse access management** — a connection whose ClickHouse user lacks `CREATE USER`, `ALTER USER`, `DROP USER`, `CREATE ROLE`, `ALTER ROLE`, `DROP ROLE`, `ROLE ADMIN` (or reading `system.users`, `system.roles`, `system.grants`, `system.role_grants`) is now saved with a warning instead of being refused. Those grants only power Admin › ClickHouse users and roles, which say the connection's user isn't allowed (`403 CLICKHOUSE_ACCESS_DENIED`) until they are granted. In the privilege report, `ok` now means every *required* feature passes; the new `complete` means every feature does (ADR 0031).

### Fixed
- **No more `system.grants` probe on connect** — connecting no longer checks whether the connection's ClickHouse user is an admin. That check failed with `ACCESS_DENIED` (and logged "Failed to check admin status" about once a minute) on users without `SELECT ON system.grants`, and missed admin rights granted through roles. CHouse UI authorises from its own roles, so nothing depended on it (#422).
- **Recent queries respect query history permissions** — the Home page and the command palette list everyone's recent queries only for admins and holders of `query:history:view:all`. Everyone else sees the queries they ran in CHouse UI on the current connection. The list now covers the last 7 days, so the log scan stays bounded.
- **`GET /api/metrics/custom` follows data access rules** — the query is checked like one from the SQL editor before it runs, so it can no longer read tables the caller's rules deny.

### Removed
- **`isAdmin` and `permissions` in the connect response** — `POST /api/rbac/connections/:id/connect` no longer returns them; they described the ClickHouse user, not the CHouse user, and were often wrong.
- **`GET /api/rbac/connections/session`** — the route was registered after `GET /:id`, so it always answered `404 Connection not found` and nothing called it.

## [v3.17.1] - 2026-11-08

### Changed
- **Some statements are refused for non-admins when they can't be fully checked** — OPTIMIZE, RENAME, SYSTEM, GRANT, SHOW COLUMNS/PROCESSLIST, table functions and engines that reach other data, `INTO OUTFILE`, materialized views with `TO`, `CREATE TABLE … AS another_table`, quoted names containing dots or spaces, and `INSERT … VALUES` rows with subqueries or dictionary lookups. Admins are unaffected. A syntax error now returns 400 with ClickHouse's message, and an unreachable ClickHouse returns 503 instead of "access denied". Unqualified names always mean the connection's default database (write `system.parts`, not `parts`).

### Fixed
- **Image and dependency security fixes** — the production image requires zlib 1.4-r0 (CVE-2026-4738), and lodash moves to 4.18.1 (CVE-2026-2950); the lodash override pinned the vulnerable 4.18.0 exactly. With the musl floor from the previous fix, a Trivy scan of the image finds nothing at any severity.
- **Per-user query and AI rate limits** — the `/api/query`, `/api/ai` and general API limits ran before sign-in was checked, so every caller on a server shared one bucket and one busy user could throttle everyone. They now count per user (browser sessions and the user's API/MCP tokens share one budget), or per client IP when signed out.
- **Secure generated passwords** — the "generate" buttons in Create user, Edit user and the ClickHouse user wizard now use the browser's secure random generator instead of `Math.random()`.
- **Explorer SQL quoting** — Create table, Query, Describe and Drop tabs quote database, table, column and cluster names, quote comments correctly, and reject a column type with extra SQL after it. A database's Query tab now opens `SHOW TABLES FROM <db>` instead of broken SQL.
- **`rbac:reset` resets everything** — it now drops every table CHouse UI creates (it used to drop only 8 old ones), and leaves other tables in a shared PostgreSQL database alone.
- **Clean shutdown** — stopping the server now also stops the AI approval sweeper, the auto-triage runner (handing its lease to another replica at once) and the Doctor scheduler.
- **ClickHouse users and roles reconnect** — these pages now recover when the server reports a stale connection (`CONNECTION_CONTEXT_STALE`).
- **API base URL** — sign-in, SSO, preferences and the other RBAC calls now honour `VITE_API_URL` and send cookies, like the rest of the app.
- **Format names** — `validateFormat` accepts every listed format in any case (only `CSV`, `TSV`, `JSON` and `XML` passed before).
- **Docs site under a sub-path** — landing-page and docs links respect `VITE_BASE_PATH`; before, the base path was never read in the browser.
- **Image: musl security fix** — the production image requires musl 1.2.5-r13 (CVE-2026-107891), so a stale base or build cache can't ship the vulnerable version.
- **Data access rules can't be bypassed through SQL ClickHouse understands but the old parser didn't** — non-admin queries are now parsed by ClickHouse itself (`EXPLAIN AST` on the same connection, no data read) and every table and database in the result is checked (ADR 0030). This closes ways a user limited to some databases could read others: `SETTINGS`/`FORMAT`/`FINAL` queries listing a second table, `x IN other_table`, `joinGet(other_table, …)`, `{t:Identifier}` parameters, subqueries inside `INSERT … VALUES`, CTE name tricks, comment text, and a `CREATE VIEW` target that was never checked. Dashboards, scheduled queries and AI tools now check exactly the SQL and parameters they run.

## [v3.17.0] - 2026-11-03

### Added
- **Upgrade check** — **Monitoring › Upgrades** shows whether the connection's ClickHouse version is still supported, when its last patch came out, and the versions worth moving to (the newest LTS recommended, a same-line patch first when one is out). **Check** compares the target with your real workload: exactly against another of your connections on the target line (settings and their defaults, obsolete settings, functions, types, engines and formats), or from the breaking-change notes between the two versions. Only changes your schema, settings profiles and 30 days of `query_log` use become findings, each with its sources, evidence, callers and the SQL to fix it or keep today's defaults; notes that name what you use are listed to judge, and **Copy as Markdown** gives a report. Release data and notes come from GitHub and Docker Hub when `UPGRADE_CHECK_ENABLED` (Helm `observability.upgradeCheckEnabled`) is on (ADR 0029)
- **Try it on this server** — a check also plans your top 200 read-only query shapes on the current server with `EXPLAIN`, once with the settings each ran with and once with the target's (the new analyzer on, plus the changed defaults in an exact check). Queries that fail only with the target's settings become findings with the setting that breaks them, their callers and the error; plans that change are a heads-up. Nothing is executed. On by default, with a checkbox to turn it off
- **Chouse AI reads the release notes** — when a model is set up, it turns the notes that matter for your workload into findings; each must cite a note and names from your workload, or it is dropped
- **Fleet version colour** — a card's version turns red when its line is out of support and amber when a newer patch is out, with the reason on hover and a link to Upgrades
- **MCP and assistant tool `get_upgrade_status`**; `run_upgrade_assessment` takes a connection to compare with
- **Sign in to MCP with OAuth** — agents connect to `/mcp` with the URL alone: they open CHouse in the browser, the person signs in (password or SSO) and picks the agent's write tools and how long access lasts, and the agent gets a token that only works on MCP. CHouse is its own OAuth 2.1 server following the MCP authorization specification (protected resource and authorization server metadata, dynamic client registration, PKCE, resource indicators, refresh-token rotation with reuse detection, revocation). Off by default; turn it on in **AI Governance › MCP › Sign-in for agents**, where administrators can also turn pasted tokens off for MCP, hold new agents for approval, limit return addresses and the longest access, and block an agent or revoke a person's access. People see and revoke their agents under **Preferences › Personal access tokens › Connected apps** (ADR 0028)

### Fixed
- **Sampling settings on newer models** — AI requests no longer fail with "`temperature` is deprecated for this model" on Claude models after 4.6 (such as Claude Haiku 5.5), or with an unsupported-temperature error on OpenAI reasoning models (o-series, GPT-5). Temperature, top P, top K and the penalties are now left out for those models, including when they are reached through Bedrock, OpenRouter or an OpenAI-compatible endpoint; other models keep the temperature-0 default
- **Dependency security updates** — `@hono/node-server` moves to 2.1.3, fixing a static-file path-decoding issue that could skip middleware, and `qs` moves to 6.16.1, fixing a crash (denial of service) in `qs.stringify`. Both come in through the MCP SDK on the server. The lint-only `minimatch` advisory is recorded as an accepted risk until eslint ships a compatible fix
- **Watch test** — the `watch_table` test no longer fails once its hardcoded end date has passed
- **Upgrade permission names** — **Admin › Roles** now calls `upgrades:view` "View Upgrades" and `upgrades:run` "Run Upgrade Checks and Codec Trials", instead of naming the upgrade readiness and canary replay that the upgrade check replaced

### Removed
- **Upgrade rollout tracker**, the six-rule readiness pack and its verdict; the MCP and assistant tool `get_upgrade_rollout` and `GET /api/upgrades/rollout` and `/rules`
- **Workload replay on a canary** — replaced by trying the workload on the current server; the `get_canary_replay` and `run_canary_replay` tools and `/api/upgrades/replays` are removed

## [v3.16.0] - 2026-10-25

### Added
- **Chat apps** — Slack and Google Chat channels gain an **App** mode (a Slack bot token and signing secret; a Google Chat app with a service account), and **Telegram** channels arrive. These channels edit what they posted — a fleet or dashboard alert shows *resolved* in place, a request shows who decided it — and carry buttons that call back to CHouse
- **Act from chat** — **Acknowledge** and **Snooze 1h** on Data Health alerts, **Approve** and **Reject** on remediation proposals, **Approve** and **Decline** on AI requests. Every press is checked by its platform, matched to an active CHouse user (Slack and Google Chat by email, Telegram by an account linked in **Preferences › Linked chat accounts**), and runs through the same route the UI uses as that person. Audited as `alerting.chat_action`
- **Who can act from this channel** — an allowlist per channel (Slack users and user groups, Google emails and domains, Telegram user IDs, CHouse users and roles) that narrows who may press its buttons
- **Need You alerts** — AI Governance › Assistant › Chobi › Alerts sends second-approver changes, background proposals and optionally held MCP calls to team channels after a delay, with Approve and Decline where the channel allows, and edits them once they are settled
- **Memory suggestions** — after a quiet Chobi conversation, up to three notes worth keeping appear as chips (**Save to me**, **Propose to team**, **Dismiss**); nothing is saved without a click, and administrators can turn it off
- **Remediation channels** — post remediation proposals to any alert channel, picked in Admin › Alerting › Rules; the Slack bot set by environment variables keeps working
- **Alerting history API** — `GET /api/alerting/events/search` with search, source, severity, channel, delivery and time filters and cursor pages; `GET /api/alerting/overview` and `GET /api/alerting/sources`; channels report delivery health and what uses them. `list_alerting` and the MCP `list_alerts` gain `sources`, `overview` and filtered `events`
- **Chobi** — the chat becomes Chobi, a buddy made of the logo's three bars that parks on the screen edge (drag to move, Ctrl/⌘ J) and stays usable above any dialog. Panels in Bubble, Docked and Focus sizes with three tabs: **Now** (what needs a look across every connection you can reach, built from data), **Chat** and **Activity** (changes waiting for you and what AI changed, with Undo)
- **Nudges** — Chobi points out new incidents, failed jobs, unreachable clusters and approvals waiting for you, from data and never an AI call; at most one every two minutes and six an hour, with mute and quiet hours per person
- **AI write tiers** — 74 write tools in seven toolkits, each checked by tier: undoable changes run at once with **Done · Undo** for 24 hours, changes undo can't reverse ask once (or once for a plan of several, with "allow in this chat / for 1 hour"), and privileged or destructive ones need a second person who holds the same permission. A production connection makes every change one tier stricter; passwords, connections, SSO, tokens, guardrails and approvals are never AI tools
- **Connection environment** — mark a connection Production, Staging or Development in **Admin › Connections**
- **MCP write tools** — the same write tools over MCP for tokens whose user has `ai:act`, bounded by an administrator ceiling (**AI Governance › MCP › Write tools**) and each token's write policy (the wrench in **Preferences › Access tokens**); a call that asks is held while you confirm in CHouse, then returns its result or a pending action id for `get_action_status`; `undo_action` reverses undoable ones
- **CHouse Assistant v3** — one agent that owns the conversation and every change: Data & Query and the page's toolkit loaded up front, others with `load_toolkit`; four read-only investigators; `navigate`, `open_entity` and `fill_form` to show a page or put SQL in the editor; plans for multi-step changes. Ships with 40 eval cases
- **Watches** — "keep an eye on this table until tomorrow": a personal Data Health check every 15 minutes that removes itself when it ends (default 09:00 tomorrow, at most 7 days, five per connection)
- **Ask from anywhere** — Ctrl/⌘ J with text selected, drop text or an item on Chobi, Ctrl/⌘ J or **Ask Chobi about this SQL** in the SQL editor, or **Ask** on a Now item
- **Hand off** — turn a conversation into a note for an incident's notebook, a Markdown file, or a short post to an alert channel (new `POST /api/alerting/channels/:id/message` and `post_alert_message` tool)
- **Plain mode** — administrators can show the CHouse logo instead of the character and turn nudges off, in **AI Governance › Assistant › Chobi**
- **Scheduled job links** — `/data/scheduled-queries/jobs?job=<id>` opens one job
- **ClickHouse privilege check for connections** — Test connection checks the connection's ClickHouse user against what every feature needs (Core, Monitoring and fleet, Data health and observability, Query control, Data editing, ClickHouse access admin) and lists anything missing as copyable `GRANT` statements, with **Copy all grants** and **Check again**. Budget policies (per query, per day, partition filters on large tables, warn or block on tables with incidents) are checked with `EXPLAIN ESTIMATE` before queries run, results carry health notices, and administrators can pause all agent access. New MCP tools: `get_dataset_health`, `get_lineage`, `get_table_context`, `get_metric`, `get_pipeline_status`, `list_incidents` and `propose_remediation` (a write tool, off until an administrator turns it on; there is no approve tool).
- **Schema change preflight** — DDL that would break dependent views, dictionaries, jobs, promises or saved queries is stopped with the impact and a safer plan; users with the new `schema:override` permission can confirm and run it anyway (audited).
- **New permissions** — `observe:view`, `observe:edit`, `context:edit`, `performance:view`, `capacity:view`, `cost:view`, `upgrades:view`, `upgrades:run`, `remediation:propose`, `remediation:approve`, `remediation:approve_high`, `schema:override`, `agents:view`, `agents:manage` and `notebooks:edit`, granted to the default roles by migration; no existing permission changes.
- **Helm chart: data observability settings** — optional `observability.*`, `remediation.*`, `publicBaseUrl` and `slack.*` (existing-secret support); every existing values file renders unchanged.
- **Cluster-aware scheduled query destinations** — materialize jobs can now create and write their destination across a ClickHouse cluster. A single-shard cluster gets a `Replicated*MergeTree` table on every replica; a sharded cluster gets a per-shard local table plus a `Distributed` table routed by a deterministic sharding key. The builder lists the connection's clusters, shows the generated `ON CLUSTER` DDL, and blocks saving until every precondition passes (cluster membership, database, Keeper macros, engine, sharding key). Each run re-checks the topology and fails instead of writing partial data.
- **AI agents managed in the UI (Agents › Assistant)** — every AI feature (the chat, SQL editor Optimize/Debug, the Doctor scan, Monitoring diagnoses, DataOps and observability assistants) now runs on an agent stored in the metadata database: prompt and task templates, model, tools, skills, subagents, harness and tuning are edited, versioned, rolled back and reset to built-in from the UI, with a test console that runs unsaved drafts. Built-in agents reproduce the previous behaviour exactly and keep receiving CHouse updates until you customize them. New permissions `ai_agents:view` and `ai_agents:manage` (granted to Admin and Super Admin) and audit events `ai_agent.*`, `ai_harness.*`, `ai_skill.*`, `ai_binding.update`, `ai_registry.reset`, `ai_registry.rollback` (ADR 0019).
- **CHouse Admin chat agent and agent picker** — the chat can now answer read-only questions about CHouse itself (users, roles, permissions, data access, connections, scheduled jobs, data health, alerts, incidents, Doctor reports, AI models, external agents, audit log) through tools that call the API as the chatting user. Pick *ClickHouse Data* (the default), *CHouse Admin* or *Auto*, which routes each question and combines answers that span both; the choice is saved per thread and the activity panel shows which subagent made each call.

### Changed
- **MCP is served at `/mcp` on the web port** — agents use the same address, Service, Ingress and TLS as the UI (`https://<host>/mcp`); the MCP endpoint starts off and answers `404 MCP_DISABLED` until it is turned on. The dock's MCP indicator opens Agents › MCP.
- **Helm chart 2.0.0** — MCP needs no chart values any more. Leftover `mcp:` values are ignored and the install notes warn until they are removed.
- **DataOps is now Data** — `/dataops/*` links redirect to the matching `/data/*` page; Scheduled Queries and Data Health keep working exactly as before inside it.
- **Fleet collection is always on** — the observability collector replaces the fleet poller and runs on every pod under per-connection leases. `FLEET_POLLER_ENABLED` / `fleet.poller_enabled` are accepted but ignored (a warning is logged); `FLEET_POLL_INTERVAL_SECONDS` still works and `OBSERVE_FLEET_INTERVAL` takes precedence.
- **Doctor reports** open as investigation notebooks with proposed fixes alongside the report.

### Fixed
- **Workload replay on a canary** — queries whose tables were dropped from the baseline are now **skipped** instead of counted as canary errors; tables missing only on the canary show as **Missing on canary** instead of errors; the replayed query text is shown without the client's `FORMAT` clause; and the most serious differences are listed first. The panel also says that the active connection is the baseline.
- **Agents › Pause all agent access** — the button and the paused banner use the yellow/amber accent instead of alarm red.
- **Explorer button on Data › Datasets** — opened an information tab for an empty database instead of the selected table; the command palette's table and database results had the same problem.
- **Role cards grouped every new permission under "Other"** — the cards now use the server's permission categories, so Data Observability, Performance & Capacity, Remediation and Agents permissions show in their own groups.
- **Invalid Data Health checks returned a server error** — saving or previewing a promise whose checks cannot run as defined (for example a row count without an event-time column, or two checks with the same key) failed with a 500. It now returns 400 with the reason, and the same applies to Chouse AI watcher drafts.
- **Fleet doctor "Propose fix"** — no longer crashes the page; the remediation catalog now returns required grants as a list, as the UI expects.
- **Dependency vulnerabilities** — upgraded `nodemailer` to 10.0.13 (fixes 2 high and 3 medium advisories) and refreshed transitive `ip-address` (10.7.3) and `fast-uri` (3.1.8) to clear the findings in the Artifact Hub/Trivy report for v3.13.0
- **Further dependency advisories** — upgraded `dompurify` to 3.4.16 and the ESLint-side `ajv` 6.x to 6.15.0
- **Accepted vulnerability exception** — documented a time-boxed scanner exception for `braces` 3.0.3 (GHSA-vfj7-8cjw-p6xm), which has no upstream fix; see `SECURITY.md`
- **Replace-mode staging for replicated destinations** — the staging table is now a plain local `MergeTree` with the destination's keys instead of a clone that reused the destination's Keeper path and failed with `REPLICA_ALREADY_EXISTS`. Every statement of a materialize run is also pinned to one ClickHouse session, so a non-sticky load balancer can no longer split staging and the partition swap across nodes.
- **AI skills now load** — the built-in skills (optimizer, debugger, evaluator, chat skills and the ClickHouse reference skills) were never actually offered to the model because of a mount-path bug; every agent now sees the skills its prompt refers to.
- **Bedrock models follow the same AI harness** — Bedrock deployments no longer get the planning, filesystem and general-purpose subagent tools the other providers have always had hidden.

### Removed
- **Dedicated MCP port and `MCP_*` settings** — port 8752, `MCP_ENABLED`, `MCP_HOST`, `MCP_PORT`, `MCP_ALLOW_WRITES`, `MCP_ALLOW_DESTRUCTIVE`, `MCP_TOOLSETS`, `MCP_ALLOWED_ORIGINS`, `MCP_TIMEOUT_SECONDS` (and the matching `mcp.*` YAML keys), plus the chart's `mcp.*` values, `<release>-mcp` Service and MCP Ingress. The server logs a warning naming any that are still set. After upgrading from 3.13, point agents at `/mcp` on the UI address and turn MCP on in Agents › MCP.
